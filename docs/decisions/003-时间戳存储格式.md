# 003 · 时间戳存储格式

| 项 | 内容 |
|---|---|
| 日期 | 2026-10-20 |
| 状态 | 生效（已回写 PRD v0.1-rev3 §8、TDD §4.8/§7） |
| 关联 | PRD §8 数据模型、F-8.2、F-9.2、F-9.5；TDD §4.8、§7 |

## 背景

PRD 原 §8 把时间戳写成 ISO 8601 字符串（`"2026-10-19T20:12:00+08:00"`）。落到实现时有三处必须用到时间：`records.jsonl` 的起止时刻、`bank/stats.json` 的记忆衰减基准、`session.json` 的快照基准。

用字符串有两种走法：自己解析/生成（时区与夏令时容易写错），或引入 `time` crate（`formatting` + `local-offset`）。两者都要为"只用来比较先后与算差值"的数据付一次代价。

## 选项

**A. 保留 ISO 8601 字符串 + `time` crate。**
好处是文件人眼可读、与日志格式统一；代价是多一个直接依赖、时区换算仍要处理（`local-offset` 在部分环境的时区探测行为并不稳定），而所有业务判断（30 天冷却、30 分钟冷却、跨午夜归属、连续天数）实际都只要整数差。

**B. 全部存 Unix 毫秒（UTC，`i64`，字段名 `*Ms`），展示层格式化。**
好处：比较与差值是一行整数运算；不引任何时间库；跨午夜只做一次整数比较再换算本地日期。代价：文件可读性差，用户手改时要自己换算（PRD §13-7 已说明文件明文、本软件不做完整性校验）。

**C. 双写（毫秒 + ISO 字符串）。**
两份数据就有两个真相，任何一处写错都是"看着对、算着错"，直接否决。

## 结论

**采纳 B。** 具体口径：

| 项 | 规则 |
|---|---|
| 单位 | Unix 毫秒（UTC 起点），`i64`，无时区信息 |
| 字段名 | 一律 `*Ms` 后缀：`startedAtMs` / `endedAtMs` / `lastAskedMs` / `wallBaseMs` / `cooldownUntilMs` |
| `records.id` | `s_<startedAtMs>`（天然唯一，不需要时区就能生成） |
| 本地日期 | 只在两处换算：① 统计层算"有效日归属"；② 展示层格式化。换算用 Win32 `SystemTimeToTzSpecificLocalTime`（`windows-sys` 已在依赖里） |
| Core 依赖方向 | Core 不直接调 Win32：注入 `LocalDate` trait，Platform 提供实现（TDD §1.2 的依赖方向不被破坏） |
| 前端 | 用 `Intl.DateTimeFormat` 按系统时区渲染；与 Rust 侧同机同时区，结果一致 |
| `monoBase` | **不是时间戳**，是单调时钟原始刻度，保持 `u64`，不要与 `*Ms` 混用 |

## 代价与取舍（写进交付物，别装作没有）

1. **可读性下降**：数据文件里看到的是 `1760875920000`。缓解：日志与界面一律打印本地时间，数据文件保持机器友好。
2. **归属日期随查看时区变化**：用户事后改系统时区，历史记录的有效日归属可能平移。这与原方案（按本地日期）语义相同——原方案里 ISO 串带 `+08:00` 看似固定，但统计仍是按本地日历日算的。属于已知取舍，不改。
3. **需要一次 Win32 换算**：M5 才用到，M1–M4 只写毫秒不换算，不影响前期进度。

## 推翻条件

出现以下任一情况，应改为"UTC 时间戳 + 显式时区偏移"（例如 `{ "atMs": 1760875920000, "tzOffsetMin": 480 }`）：

1. 需要跨设备同步或多人共享记录（v0.2 及以后若破例引入云端）；
2. 用户要求"按记录当时所在时区"统计历史，而不是按查看时的时区；
3. 出现需要在文件层面直接阅读时间值的运维场景（例如排障要求手工比对）。

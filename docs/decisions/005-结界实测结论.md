## 1. 抢焦点（S3）

**做法**：`SetWinEventHook(EVENT_SYSTEM_FOREGROUND, WINEVENT_OUTOFCONTEXT)` 装在独立线程，事件投递到该线程的消息队列；回调里比较前台窗口的**进程 id**，不是本进程就 `SetForegroundWindow` 抢回来。连续失败不放弃，只降频记日志。

**实测**：把前台切到 `ApplicationFrameHost`（pid 3300），800 ms 后前台 pid 回到 10632（本进程）——**抢回成功**。

**为什么按 pid 而不是按句柄**：主窗口 + 副屏 `display-N` 都是我们的，按句柄要维护一份集合且随副屏增删变化；按 pid 一次判定覆盖全部。

## 2. 阻止睡眠（S4）

**做法**：`SetThreadExecutionState` 的请求是线程级的，设置与清除必须在同一线程，所以专门开一条线程持请求，主逻辑只发信号。只加 `ES_SYSTEM_REQUIRED`，不加 `ES_DISPLAY_REQUIRED`（允许熄屏，F-3.8）。

**实测**（A-10 调整口径，见 D-23）：

```
powercfg /requests
SYSTEM:
[DRIVER] USB Audio Device ...
[PROCESS] \Device\HarddiskVolume4\CodeBuddy_text\biguansim\src-tauri\target\debug\biguansim.exe
```

闭关期间能看到本进程的 SYSTEM 请求；DEV 退出后再查，`biguansim` **不在列表里**——解除干净，没有残留。

## 3. 显示变化（S6）

**做法**：1 s 轮询显示器快照（数量 + 坐标 + 分辨率 + DPI 缩放，按坐标排序后比对），**连续 2 次**不一致才判定 `accident`，任一次回到基线即清零。

**为什么不用 `WM_DISPLAYCHANGE` 消息**：Tauri 窗口消息由 tao 消费，挂钩子要侵入上游；轮询 1 s 的开销可忽略，且"连续两次"这个去抖逻辑本身需要采样，轮询更自然。

**验证边界（如实说明）**：本机是单屏台式机，**拔屏无法实测**。已把"一次抖动不算、连续两次才出关、中途回基线清零"抽成纯函数 `advance()` 并写了 3 条单测。真机拔 HDMI 的验证留给你，记为 A-12 待确认。

## 4. `Win` 键处理（2026-10-20 三组对照实验，仍有疑点）

**用户实测到的两个故障**：

1. 单击 `Win` 弹出开始菜单；
2. 之后按 `s`/`d` 变成 `Win+S`/`Win+D`（把搜索与桌面翻出来）——键盘"半死"。

**根因（第一版实现）**：当时是"按下放行、抬起吞掉"，想让开始菜单别弹，结果系统认为 Win 一直按住，后续每个键都成了 `Win+X`。

**对照实验**（`examples/hook_probe.rs`，合成按键，前台窗口是 IDE）：

| 策略 | 开始菜单 | 后续按键变 Win+X |
|---|---|---|
| 放行按下 + 吞掉抬起（旧实现） | 弹 | **会**（就是用户遇到的现象） |
| 吞掉按下 + 放行抬起 | 不弹 | 不会 |
| 按下与抬起都吞 | 不弹 | 不会 |

**当前实现**：按下与抬起**都吞**，系统完全看不到 Win；`Win+L` 由 hook 线程调 `LockWorkStation()` 代劳（F-3.4 语义不变）。另加每秒 `GetAsyncKeyState` 校正，专治锁屏/安全桌面导致的抬起丢失。

**仍存疑（需真实键盘复验）**：同一套代码在**应用内**用合成按键测试时，Win 仍会拉起搜索；在**探针**里却拦得住。怀疑是 `keybd_event` 注入事件与真实键盘走了不同路径，或判定被残留的搜索窗口污染。因此**不能宣布 Win 键已完全拦住**——请用真实键盘确认单击 Win 与随后打字的表现，再决定是否需要在 PRD §13 补一条局限。

## 5. 亮度（S5，延后）

本机是台式机，显示器亮度由显示器物理按键控制，DDC/CI 与 WMI 都改不了；没有可测设备，做了也无法验收。**延后到 v1.0 之后**（D-22），接口约定已写进 M3 计划 S5，将来实现不返工。连带：A-14 在 v0.1 标"延后，不阻塞发布"，省下一次 `windows` crate 的引入。

## 1. 这份文档管什么

**管**：阶段顺序与依赖、每阶段的出口条件、25 条验收用例的归属、跨阶段门禁、需要人拍板的卡点。

**不管**：某阶段具体先改哪个文件、某个函数怎么写。那是 `docs/plans/` 下各阶段计划的事（本文件 §8 定义其写法与书写时机）。

**原则**：本文件只写"可判定"的内容——每条出口条件都能回答"做到没做到"。判定不了的（如"界面好看"）一律降级为具体可核对项（截图分辨率档位、元素不溢出）。

## 5. 跨阶段门禁（每阶段收尾都必须过）

1. **静态检查**：`pnpm verify`（format:check → lint → typecheck → cargo fmt → cargo clippy）全绿，0 error 0 warning。
2. **自动化测试**：`cargo test` 全绿；`vitest` 全绿（仅纯函数）。附输出摘要，不写"我改好了"。
3. **手工项**：需要真机/观感的项按 TDD §8.2 出勾选表 + 截图（暖白/暗色 × 1366×768/4K），未测项标"未验证，需要你确认"并给复现步骤。
4. **文档同步**：阶段计划原地标注完成日期；行为或接口有变则同步 PRD/TDD/README（AGENTS §7）。
5. **交付四件套**：做了什么/为什么、验证证据、commit hash、未验证项与残余风险（AGENTS §8）。
6. **防复发物**：每个 bug 修复留下回归测试、检查脚本或一条规则（AGENTS §7）。

## 8. 计划文档的写法与书写时机（回应你的疑问）

**结论：总计划一次写全，阶段计划到点再写。**

| 文档 | 何时写 | 内容粒度 |
|---|---|---|
| 本文件（总计划） | 现在一次写完；只在阶段边界/口径变化时改 | 阶段顺序、依赖、出口条件、验收归属、卡点 |
| 阶段计划（`<日期>-M<n>-<主题>.md`） | **该阶段启动那天写**，写完才动代码 | 可执行的步骤序列、每步验收、文件清单、偏离登记 |
| spike 清单（如 M1 拦键） | 与所属阶段计划同一天写 | 必须先验的五件事与失败后的降级路径 |

**为什么阶段计划不提前写**（三条，按重要性）：

1. **提前写的细节必然是猜的。** M3 的拦键状态机取决于 spike 实测，M4 的抄写交互取决于 M2 定型的 `Lock.vue` 投影结构。现在写只能写出"大概这样"，而 AGENTS 元原则要求每条约定可判定——猜出来的步骤判定不了。
2. **会与实现分叉，plan 反而失去约束力。** 一份和代码对不上的计划，读一次就没人再看；到了真要执行时还得重写，等于写了两遍。
3. **总计划已经足够防止"漏活"。** 漏项风险由 §4 的 A-1~A-25 归属矩阵覆盖，不靠阶段细节承担。

**代价**：无法提前给整条链路的工作量。补偿手段是总计划给出每阶段估时与依赖图（PRD §16 的立项期粗估 + 阶段计划细化后的实测值，两者不一致时以阶段计划为准并登记偏离），够用来判断"现在能不能开工"。

**例外**：如果将来有第二个人并行开发，或某阶段要交给外部执行，"按需写"要改回"提前一次写全"——那是唯一推翻本条的条件。

**阶段计划模板**（六个固定小节，缺一节不算写完）：

```
# M<n> · <主题> 计划
状态：未开始 / 进行中 / 完成 YYYY-MM-DD
1. 目标（一句话）与不做什么
2. 前置条件（依赖的阶段、环境、已定型接口）
3. 步骤序列（S1…Sn，每步：改什么、产出什么、怎么判定这一步完成）
4. 阶段出口条件（勾选表，含自动化与手工两部分）
5. 偏离登记（执行中偏离本计划必须在此记录原因）
6. 未验证项与残余风险
```
